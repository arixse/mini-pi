## 背景 Situation

起点是一次架构评估（Plan-and-Act / Maker+Checker 两条路线）。核对现状后
得到两个结论：

- **Plan-and-Act：暂缓**。plan 状态无处存放（会话是 jsonl，落进消息会污染
  上下文）、提示词膨胀会计入压缩的固定开销，而它能补的"长任务目标漂移"
  在本项目（多数任务 5~20 轮，远不到 `maxTurns` 上限）不是主要矛盾。
- **Maker+Checker：可做，但缺两个前提**。`review` 角色早就存在，契约也齐，
  可是：
  1. **没有验证手段**——它只能读代码，"改完能不能编译、测试过不过"这类
     事实性问题回答不了，评审意见可能整段建立在错误前提上；
  2. **没有观测手段**——委派给父会话的只是一条 toolCall/toolResult，
     卡片只有轮次/token/耗时，**无法区分"读过代码又真跑了验证"与"只读一遍
     就下结论"**。

## 任务 Task

1. 给 `review` 补验证能力，但**不能**用"给它 bash"这种方式；
2. 让委派结果层能看出"它到底调用了什么工具"；
3. 顺带把文档的重复与漂移收口（评估过程中发现文档已成信息瓶颈）；
4. 补开源许可，并注明商用需授权。

## 行动 Action

### 1. `verify_command`：受限验证工具（`src/agent/tools/verify.ts`，276 行）

**不给 review 完整 bash**：bash 能跑 `rm` / `git push` / `npm run deploy`，
等于把"我只评审、不改代码"这个承诺交还给模型的自觉。`review` 的输出契约
依赖它的工具边界，这与 `allowWrite:true` 被 review 忽略是同一个道理。
但完全不给执行能力，评审就只能停在"读代码觉得对不对"。

落地形态是**结构性收窄**，不是提示词劝阻——结构性阻断与"depth 到顶时不注册
`task`"同一手法。

**执行委托给 `bashTool`**，不在 verify 里重写一遍：超时、进程树清理、
`checkBashCommand`（工作区逃逸 + 凭据文件）只有一套实现。于是两道闸叠加：
白名单（本模块）拦"跑什么"，路径守卫（bash）拦"跑在哪"。

白名单的两条关键设计：

- **先禁 shell 元字符**（`| & ; < > $ \` ( ) 换行`），再匹配 token 前缀。
  顺序不可换：少了前者，`pnpm test && rm -rf x`、`pnpm test | sh`、
  `npm test > /etc/x` 全都能挂着合法前缀混过去。
  代价是 `pnpm test 2>&1 | head` 这类收窄输出的写法也用不了——可接受，
  工具描述里已提示模型改用更精确的参数。
- **`run <script>` 的 script 名单独设闸**：`npm run deploy` 是"合法 npm 用法"，
  却是把评审角色变成部署角色的那道门。只有 `test/build/lint/typecheck/check/
  verify/compile/coverage` 这类验证语义的名字放行。
  同理 `npx` 不按包管理器收口（它没有 `test` 子命令语义），改为"跑哪个程序"。

权限边界上有两个刻意的不对称：

- `verify_command` **不在** `READ_ONLY_TOOL_NAMES`（跑测试会写产物）→ 仍逐次审批；
- 但它**进** `MUTATING_TOOL_NAMES`（会起进程）→ review 委派**不再可并发**。
  `subagent.test.ts` 原有"review 可并发"的断言因此被推翻，已同步并注明原因。

预算也要跟着调：review 墙钟 60s → **100s**、轮次 10 → **12**。
给验证能力却不给时间，等于跑到一半被超时打断。仍保持 `review < explore(120s)`
的既有排序。

**闭环靠结论契约，不靠状态机**：review 必须给出可判定的 PASS / FAIL + 阻塞项，
判定权留给父 Agent。在 loop 层加强制 gate 会破坏"执行顺序只有 `runAgentLoop`
一个实现"这条性质，而且确认次数翻倍，不划算。

### 2. 委派可观测性（`SubAgentResult.toolCalls`）

三个决定都来自"要能据它判断模型有没有偷懒"：

- **按调用顺序记录、允许重复**——顺序本身是信息（先读后跑 ≠ 先跑后读）；
- **只看 assistant 的 toolCall，不看 toolResult**——被审批或白名单挡回的调用
  同样是"它做了什么"的证据。"想跑 `pnpm test` 被挡回"与"根本没想跑"是
  完全不同的两件事，丢了会误判；
- **一次都没调用时字段缺省**（不写空数组）——"没观测到"与"确认没有"
  必须可分。

去向也分了层：进 `/last` 的 details 与卡片尾部（「用了 read_file×3、
verify_command×2」），**不进** `formatSubAgentResult`——工具清单进模型正文
是纯成本。卡片聚合按**首次调用顺序**，超过 4 种工具就截断：全量列表会把
真正要找的那个挤出行尾之外。

### 4. 文档漂移的门禁（`src/docs.test.ts` 新增，311 行）

文档能腐烂是因为**只有人肉复核**。新测试只断言结构性事实，不断言文案
（文案随时改写，绑定原文会让测试变成改文档的拦路虎）：

| 断言 | 挡住的漂移 |
| --- | --- |
| Markdown 相对链接指向的文件存在 | 文档改名后满地悬空链接 |
| 反引号里的 `src/` `test/` 路径存在 | 引用已删除的模块（白名单只放未实现的 `src/server`、`src/client`） |
| 每份文档都被别的文档链接到 | 孤立文档迟早腐坏 |
| 「xxx.md §N」的章节真的存在 | 内容一搬家（命令表从 cli-interaction 挪走），散落的"见 §5.2"全指向空气 |
| README 的入口性（安装/命令/文档表） | 入口退化成正文副本 |
| docs 数值与实现一致（角色超时、上下文窗口表、压缩阈值） | 改代码忘改文档的数值 |

### 5. 许可（`e637c3a`）

此前只有 `package.json` 里一句 `license: "ISC"`、仓库里**没有 LICENSE 文件**
——既没有生效条款，也无法声明"商用需授权"。

- 新增 `LICENSE`（自定义协议 v1.0）：非商业免费（使用/复制/修改/分发），
  商业用途须**事先书面授权**，并把"机构经营活动中内部使用""集成进收费产品"
  "收费托管""代客交付、竞标"逐条点明——只写"禁止商用"会让企业用户以为
  内部自用不算；
- `package.json` 改 SPDX 的 `SEE LICENSE IN LICENSE`（把条款外置到文件）；
- README 拆出「范围」「许可」两节，用表格逐场景说明是否需要授权，并明确
  **限制商业使用不属于 OSI 认可的开源**（source-available），避免下游
  按开源选型；
- **LICENSE 不在 `files` 白名单却仍会进包**——它和 README 同属 npm 固定保留
  文件（`npm pack --dry-run` 实测 4 个文件、345KB）。白名单里再写一遍是冗余，
  但 publish.yml 补了 `test -f "$PKG_DIR/LICENSE"`：meta 指向的文件一旦没进包，
  用户装完就只剩一句指向虚空的声明。

## 经验总结 Key Learnings

1. **"给能力"与"给权限"是两件事，中间那一层叫结构性收窄**。review 需要的是
   "能验证"，不是"能执行"。把需求拆成"需要哪些动作"再映射成白名单，比
   给 bash + 提示词劝阻可靠得多——提示词是建议，工具边界是事实。

2. **白名单的第一道闸是元字符，不是前缀**。任何"命令前缀白名单"若不在前面
   禁掉 `| & ; > $ \``，都只是形式上的白名单（`合法前缀 && 为所欲为`）。
   这类守卫的**判定顺序**本身就是安全属性，值得写进注释。

3. **"合法用法"里藏着跨界的那道门**。`npm run deploy` 语法完全合法，
   挡它的不是语法而是语义。黑名单/白名单要按**意图**分类（验证 vs 部署），
   不能按**形式**分类（是不是 npm 命令）。

4. **可观测性要观测"意图"而不只是"结果"**。只看 toolResult 会把"被拒绝的
   调用"判成"没做过"，从而把"想跑测试但被挡住"误判为"模型偷懒"。
   记录工具调用时，被拦截的调用与成功的调用同等重要。

5. **文档的重复迟早变成文档的分叉**。命令表三处各写一遍时，只是"多维护两份"；
   等它开始不一致，读文档的人（包括 agent 自己）就得先判断哪份可信。
   拆分的依据不是篇幅，而是**一份事实只有一个权威位置**。

6. **测试文档也要守"结构不守文案"**。断路径存在、链接可达、章节号存在、
   数值与代码一致——这些是事实；断言某句原话会被写进去，等于给每次改文档
   上锁。文档测试的选题标准：这条断言失效时，是否**必然**意味着文档不可信。

7. **打包白名单之外还有一层"npm 自动带上"**。LICENSE / README 属于后者，
   所以"白名单里没有它"不等于"包里没有它"。反过来说，依赖这类隐式行为时
   要在 CI 里显式断言文件真的在包里——隐式一旦失效，失效方式是静默的。

8. **合并本身要跑一次门禁**。分支上绿不代表合并后绿（本次合并是 ff 形态、
   内容等价，仍跑了一遍 `pnpm check`），且**门禁偶发红要复跑再判断**：
   本次第一次跑出 1 fail / 用例少 1，复跑即绿，是 Day 22 记录过的
   负载敏感假失败，不是回归。
