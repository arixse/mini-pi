### 顺带查出并修掉一个真 bug（不是环境问题）

修完卫生问题后 tools.test.ts 仍剩 2 例失败（`真实超时应被终止并标注 timedOut`、
`失败结果必须标记 isError`），根因**不是沙箱**：

- `killProcessTree` 里 `spawnSync("taskkill", ...)` 后**无条件 `return`**，
  而 `spawnSync` 在可执行文件起不来时**不抛异常**，只把错误放进返回值
  （实测本机沙箱：`spawnSync taskkill EBUSY`、`status: null`）——
  于是 `catch` 永不触发、`child.kill("SIGKILL")` 永远不可达，超时静默失效。
- 修法：新增导出纯函数 `taskkillSucceeded({error,status})`（仅 `status === 0` 且无 error
  才算成功），`killProcessTree` 据此判断，失败则回退 `child.kill("SIGKILL")`。
- 补回归用例：`describe("taskkillSucceeded（超时终止的成败判定）")` 覆盖
  success / EBUSY(status null) / status undefined / 非零退出四种输入。

## 第三次全项目审查（只读，未改动代码）——聚焦性能热点

用户再次问「当前项目有什么优化点」。前两次已覆盖文档漂移与测试卫生，本次新查出的一批
（**均未在前面记录里**，是这次的增量结论）：

### 性能热点（长会话下最明显，头号问题）

- **一个 turn 内 `buildContext()` 被调用 4 次、`estimateTokens()` 3 次**，每次都从 leaf
  回溯整条 parentId 链并**逐字符**扫描全部历史，还要对每条 assistant 消息的
  `block.arguments` 做一次 `JSON.stringify`。调用点：
  1. `handleLine` 开头 `needsCompaction()`（buildContext + estimateTokens）
  2. `onTurnEnd → appendAgentMessages → syncContext()`（buildContext）
  3. `onTurnEnd → compactContext → needsCompaction()`（buildContext + estimateTokens）
  4. `compactContext → compactIfNedded()`（buildContext + estimateTokens）
  5. 压缩成功后再 `store.buildContext()` 一次
  → 会话越长越慢，且 `maxTurns=100` 时是 100× 这个量级。
  修法：`buildContext` 结果按 `leafId` 缓存（entries 只在 append 时增长）；
  `estimateMessageTokens` 按 entry id 记忆化（消息不可变）。
- **`compactionBudget()` 每轮重算固定开销**：`JSON.stringify(tools)`（7 个工具全量 schema）
  + `estimateTextTokens(systemPrompt)`（含 AGENTS.md，可能几万字符）。systemPrompt/tools
  在一个会话内基本不变，应缓存，在 `/reload`、`/model`、`/load skill` 时失效。
- **`createWorkspaceIgnore()` 每次工具调用都重读 `.gitignore` 并重编译全部规则**：
  `list_files` / `glob` / `grep` 各调一次（tools.ts:141/315/404）。只读工具会被并发批
  量触发，等于一次 batch 重读 N 遍。应按 mtime 缓存 matcher。
- **`walkEntries` 里 `await visit(...)` 是串行的**：grep 最坏顺序读 5000 个文件。
  应改成有上限的并发（如 8）。同时 `loop.ts` 的只读并发批 `Promise.all` **没有并发上限**，
  一批几十个 glob/grep 会瞬间开大量 fd。
- **`appendMessage` 一条消息一次 `appendFile`**：一轮十几条 = 十几次 fs write，应批量追加。
- **会话文件膨胀**：bash 的 `details.stdout/stderr` 是未截断原文（上限 4MB），
  而 `content` 已 cap 到 20000 字符；details 会原样写进 JSONL，`loadOrCreate` 又是全量
  readFileSync + 逐行 parse，长会话启动会明显变慢。

### 状态与结构

- **`toolStartCache` / `lastToolCall` 是模块级全局变量**（repl.ts:842-849）。多 REPL 实例/
  并发测试互相污染；且被 block 或未执行的 toolCall **永不产生 end 事件**，缓存条目只增不减。
  源码注释已自认「后续可整体收进一个渲染上下文对象」。
- **`runAgentLoop` 累积的 `events` 数组无人消费**：全仓无 `.events` 非测试引用，REPL 只取
  `newMessages` 并靠 `onEvent` 实时消费。100 轮 × 每条事件还持有完整 message 引用。
- **`resolveInsideWorkspace` 每次同步 `realpathSync`**（含 `realpathAllowMissing` 的逐级
  realpath 循环），read/write/edit 每次调用都阻塞事件循环一次，可加短 TTL 缓存。

### 复核：前两轮查出但仍未修的项（本轮再次确认成立）

- 7 个 provider 的 `getModelList` 裸 `fetch`，无 timeout 无 signal（模型请求侧有 120s +
  静默看门狗，这侧没有）→ `/model` 上游挂死会永久卡住。
- `OpenAIModel` 完全不读 `config.maxTokens`（model.ts 只有 AnthropicModel 在 947/996 行用），
  但 repl.ts 在 `stopReason === "length"` 时提示「调大 settings.json 的 maxTokens」——

### 多 Agent 开发方案（设计稿，未实施）

用户要求输出多 Agent 方案、明确不执行。产出 `docs/multi-agent-design.md`。

核心决策：把「委派」做成工具 `task`，而不是另起一套 Agent 运行时。
- 委派天然是 toolCall + toolResult → 自动满足「一一对应且同序」的协议约束，
  也自动随主会话 .jsonl 落盘，无需新存储格式。
- 子 Agent = 再调一次 `runAgentLoop`（换 systemPrompt / messages / tools / maxTurns），
  不写第二套循环。
- 工具集由父注册表**派生**（filter），不是重建。
- depth 到顶时注册表里**不注册** task → 结构性阻断递归，而非靠提示词自觉。

三条边界：上下文只出不进（子不读父历史，只回传裁剪结论）；
权限继承（同一份 beforeToolCall，子 Agent 的写操作仍逐次审批并带 `[子 Agent depth=N]` 前缀）；
取消级联（linked AbortController，finally 里摘监听器）。

注意区分两个维度：`READ_ONLY_TOOL_NAMES` 只表达「免审批 + 只读」这一唯一事实；
并发安全性是另一个维度，另用 `canRunConcurrently(call)` 表达（M5 并行 fan-out 用），
两者不得混用，否则出现「能并发却要确认」。

里程碑：M0 契约 → M1 单子 Agent → M2 权限与取消 → M3 CLI 呈现
→ M4 角色预设(explore/implement/review) → M5 并行 fan-out + 预算。
