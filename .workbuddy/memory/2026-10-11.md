## CLI 展示层收尾：审批 [y/N/a] + 风险着色 + /status 折行 + 命令清单注册表

延续 2026-10-10 的 CLI 展示优化，把剩下的 P2 都做掉了（commit `4c037ca`）。

### 做了什么

- **审批 `ApprovalAnswer`**：`confirm` 的返回值从 `boolean` 换成
  `"yes" | "no" | "always"`。`a`（本会话全允许）没法用真假两态表达；
  Fail closed 的语义没动，直接回车仍算拒绝（与 `[y/N]` 里 N 大写一致）。
- **`assessToolRisk`**：在审批这一层再评估一遍风险——沙箱只挡越界路径，
  挡不住 `rm -rf build` 这种**合法但致命**的命令。high 与 elevated 两档，
  **命中 high 时不叠加 elevated**（一次列五条会把致命那条淹掉）。
- **版式收编**：审批提示改用卡片的 `│ / └`（ASCII 降级 `| / +`），
  此前它自成一套三空格缩进。
- **`onSessionAllow` 回写 `trusted`**：用户按 `a` 而不回写的话，
  `/status` 会显示"需确认"而实际已经不问了——状态与实际不符比少一次确认更危险。
- **`/status` 长值折行**：新增 `width.wrapToWidth` / `terminalWidth`，
  续行缩进到值起点；值列保底 24 列。
- **命令清单单一注册表 `src/cli/commands.ts`**：`/help` 与启动欢迎语都从它渲染，
  并用 `commands.test.ts` 双向比对 注册表 ↔ `repl.ts` 分派分支 ↔ README ↔ cli-interaction.md。

### 踩到的坑

- `padToWidth` 在文本恰好等于目标宽度时会多补一个空格（保证标签与值之间有间隔），
  用它排 `/help` 的用法列会导致最长那一行偏移一列；对齐到固定列宽应自己补空格。
- `wrapToWidth` 折出来的行要 `trimEnd`：`"aa   bb"` 在 3 列宽下会得到 `"aa "`，
  尾随空格在终端里看不见却会让断言失败。
- 续行缩进容易差一格：`│ ` 的 gutter 只占 1 个字符，挂行缩进应是 `valueStart - 1`
  而不是 `valueStart`。
- 给 `describeToolCall` 加 `task` 分支时发现多行命令/goal 会让正文掉出 gutter，
  补了 `oneLine` 压平——提示语每行只有一个 gutter 前缀。

### 后续：§6.1 / §6.2 补完（commit `e92f3f8`）

- **回合脚注 `formatTurnFooter`**：`↳ 8.6s · ↑1.2k ↓318 · 上下文 3.4k/6.0k`。
- **`contextUsage()` 收口**：上下文中期口径此前在 `/status` 里各算一遍，
  加脚注就是第三份——同一刻显示两个数比没有数更糟。类似地，
  凡是"同一个刻度要在两处显示"的，都应先抽一个取数函数。
- **`printResumedSession`**：恢复历史时回放最后一问 + 最后一答。
  设计稿里的 `/history` 从未实现，脚注只提示真实存在的命令——
  **照抄设计稿前先确认里面提到的命令真的存在**。
- 顺手删掉 `printSessionInfo`（无人调用，且已被上面的回放取代）。

## 多 Agent 修复 B~E 批（commit `5d3b759`）

按 `docs/multi-agent-fix-plan.md` 一次性做完 B/C/D/E 四批，合入一个 commit。

**E 清理**：删 `subAgentToolNames`、`resolveSubAgentTurns`、supervisor 死参数；
并发判定改用 `resolveSubAgentTools` 的最终工具集。

### 过程中发现并修掉的真问题

1. **超时信号接错地方**：`linkSignals(...)` 的返回值建好却没下发，循环拿到的是另一个
   只监听父信号的 controller，于是 `timeoutMs` **永远不生效**。是测试先发现的
   （`result.timedOut` 恒 `undefined`）。
   教训：多路信号合并时，"哪个 controller 记哪个原因"必须和"下发给循环的是哪个"一起验证。

2. **`ok` 判定的用例走不通真实链路**：`loop.ts` 一遇 `stopReason === "error"` 就
   `finishTurnEarly`，而网络重试发生在 model provider 内部（不进历史）。
   所以 `[error, stop]` 只能直接喂消息列表——这反过来证明成败判定本就该抽成纯函数。

3. **`/subagent trace` 写盘失败时丢弃了 `traceEnabled`**：恰好在用户最需要 trace 的时刻
   让它不生效，且与委派开关的 `persistFailed` 处置不一致。已统一为"本会话照样生效 + 告警"。

4. **E3 的测试纠正了我的预期**：父表只读 + `allowBash:true` → 判**可并发**是对的
   （父表没有 bash，申请了也拿不到，实际能力确实只读）。E3 的口径就是"实际能力"，不是"名义角色"。

### 顺带修的样式回归

批次 D1 缩进改造时把 `ctx.style.dim(gutterGlyph(ctx))` 弄丢了，
`render.test.ts` 的 `assert.ok(markedText.includes("<d>│</d>"))` 抓到。
修法：`gutterPlain`（纯文本，用于宽度测量）与 `gutterWithIndent`（着色，用于输出）分开。

### 三条值得记住的经验

1. **跨模块会丢掉窄化**。`runAgentTurn` 里 `options.model` 是 `LlmModel | null`，

## 系统提示词重写：工具指南 / 代码风格 / 错误处理 / 项目技术栈

原提示词只有十几行（身份 + 工作目录 + "请用中文回复"）。问题不在短，而在
**没写的那部分模型会用最常见的默认补齐**，而这个默认几乎总是不对：
它会整本读大文件、用 `write_file` 整文件重写、编一条 `npm run typecheck` 去验证。

### 做法

- `src/cli/prompt.ts`：`buildSystemPrompt({ workspaceRoot, fixedContext, skillSummary, projectStack })`，
  段落顺序固定（角色 → 工作区 → 工具 → 风格 → 错误 → 项目 → 输出），
  **固定上下文与 Skill 摘要恒放最后**——它们是每次启动都可能变的内容。
- `src/cli/projectStack.ts`：`detectProjectStack()` 读 `package.json` / lock 文件 /
  `tsconfig.json` / `.git`，非 Node 项目认 Python / Go / Rust；`formatProjectStack()` 渲染。
  探测全部 try/catch，失败退化成"没探测到"，不能让启动崩掉。

### 三条刻意的取舍

1. **常用命令不收 `dev` / `start`**：那是长驻进程，而 `bash` 默认 30 秒超时，
   列进去等于请模型跑一个必然挂到超时的命令，还拿不到验证结论。
   只收跑完就退出的 `test` / `typecheck` / `lint` / `build`。
2. **只列项目里真实存在的 script**：编一条不存在的命令，模型照着执行拿到报错后
   会怀疑是自己改坏了，比不给更糟。包管理器前缀也要对（`pnpm test` 而非 `npm run test`）。
3. **探测不出东西时整段省略**：塞一句"技术栈：未知"只是噪声，还会让模型觉得这里有答案。

### 代价控制

系统提示词每次请求都带上，且计入 `contextOverheadTokens`。所以每加一段都要能回答
"少了它模型会犯什么错"。`prompt.test.ts` 里有一条上下限断言（当前约 1.9k 字符，
上限 6k）兜着，防止它慢慢膨胀。

### 验收

965 tests / 0 fail / 3 skipped（941 → 965，新增 24 条）；
覆盖率 87.53 / 91.51 / 92.97（门槛 85 / 85 / 90）。

## CI 门禁（commit `abcd489`）

`.github/workflows/ci.yml` **本来就存在**，但跑的是 `typecheck` + `test`——
覆盖率门槛（85/85/90）只在 `test:coverage` 里，也就是只在 `pnpm check` 里，
所以"覆盖率掉了"从来拦不住 PR。

### 改了什么

- 只跑 `pnpm check`，**刻意不拆成 typecheck + test 两步**：拆开必然漏掉门槛。
  原则是"CI 跑的命令 == 本地自检的命令"。
- `node-version: 23` → `node-version-file: .nvmrc`（新增 `.nvmrc` = `22`）。
  Node 23 是 2025-06-01 就 EOL 的奇数版，门禁一直跑在没安全更新的 runtime 上，
  且与本地的 22 不一致。版本只在一处声明（pnpm 走 `packageManager`，
  Node 走 `.nvmrc`），与文件里已有的哲学一致。
- 加 concurrency（取消同分支过期运行）、`permissions: contents: read`、
  job 10 分钟超时。

### 验证门槛真的能拦

用不可能达到的阈值跑一次确认退出码非 0：
`tsx --test --experimental-test-coverage --test-coverage-lines=100 ...` → exit 1。
**"装了门槛"和"门槛会让 CI 变红"是两件事，后者必须实测。**

### 还没做的（需要仓库权限，不是代码能解决的）

工作流只是"会跑"。要成为真正的门禁，还要在
Settings → Branches → Branch protection 里把 `CI`（`check` job）设为
**Required status check**。已写进 README 的"持续集成"一节。

### 一个已知的覆盖缺口

CI 只跑 ubuntu-latest。而这个项目在 Windows 上开发，`bash.ts` 有 `taskkill`、
测试里有 `IS_WIN32` 分支——Linux 上这些分支根本不执行。加 `windows-latest`
能补上，但我无法预验 GitHub 的 Windows runner 上是否全绿，冒然加会让每个 PR
都红。留作可选项。

## npm 发布工作流（commit `590e13b`）

新增 `.github/workflows/publish.yml`：推 `v*` 标签即发布，版本号**以 tag 为准**
回写 `package.json`。流程：install → `pnpm check` → `build:cli` → 定版本 →
预检 → 打包校验 → publish（带 `--provenance`）。

### 三个关键决策

1. **`files` 白名单是 bin 产物进包的唯一途径。** `bin/mini-pi-cli.cjs` 是构建产物、
   写在 `.gitignore` 里，而 npm 打包默认读 `.gitignore`。不靠 files 捞回来，
   发出去的包就没有可执行文件——用户装完 `mini-pi` 直接 command not found，
   而 pipeline 全程绿灯。已实测确认 files 优先级高于 .gitignore。
2. **包里不带 `src`。** CLI 是 esbuild 自包含 bundle，运行时不需要 TS 源码；
   `src` 只服务于仓库内开发用的 `bin/mini-pi.js`（那个入口也不在发布白名单里）。
   包从 622KB 降到 333KB / 3 个文件。
3. **发布任务不能 `cancel-in-progress`。** publish 传到一半被取消会占住版本号，
   重跑必 403。所以固定 concurrency group 排队，不取消。

### 踩到的坑

- **files 里的文件无法被 `.npmignore` 排除**：本想带 src 再剔除测试文件，实测无效，
  且 `src/**/*.test.ts` 这种中间 `**` 的写法本身匹配不到。解法不是修 ignore 规则，
  而是重新想"包里需要什么"——答案是压根不需要 src。
- **不能断言 tarball 内 bin 的可执行位**：tarball 里是 644，npm/pnpm 安装时才补 755。
  已实测安装后 `node_modules/.bin/mini-pi` 正常生成。
- **冒烟只能做语法检查**：CLI 没有 `--version`，`main()` 会起 REPL 占住 stdin，
  在 CI 里真跑会挂到超时。所以是 `node --check` + shebang + 文件存在。

### 还没做的

首次发布前需配 `NPM_TOKEN` secret（npm 的 Automation 令牌，带 2FA 的 Publish
类型会在 CI 卡住）。发布不会自动建 GitHub Release。
