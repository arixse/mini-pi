# 客户端多工作区方案

> **状态**：已落地（W1 服务端 / W2 前端 / W3 记忆与启动恢复三期均已合入
> `feature/multi-workspace`）。本文保留"为什么这么做"的推演，行为事实仍以代码与
> [technical-solution.md](./technical-solution.md) 为准。

## 0. 结论先行

单工作区**不是 bug，是当前最省事且最安全的落点**；但"两个项目来回切、
切走还想让旧任务继续跑"是真实需求，值得做。做法不是改内核，而是
**服务端从单宿主变宿主池**（一个根一个 `WorkspaceHost`，池里可以有几个），
前端侧栏**根节点仍是「工作区」，它下面挂多个工作区名节点**——层级保持
三层：工作区 → 工作区名 → 会话（Run 不再作为侧栏叶子，Run 的展示仍归
会话时间线）。会话寻址必须 root 作用域
（sessionId 是文件名，跨工作区会撞），这是整个方案里唯一容易静默出事的点。

```
方案A（推荐） 宿主池：一个进程管 N 个 WorkspaceHost，activeRoot 决定"新任务去哪"
方案B（被否）  每工作区一个 serve 进程/端口：改动最小，但审批聚合、通知、
              全局并发都没有落脚点，桌面壳的单实例锁也挡多端口
方案C（被否）  靠多标签页：切工作区就销毁宿主，多标签互相踩（审批与状态
              互相覆盖），等于把并发安全放到用户手里
```

## 1. 现状（实施前）：单活动工作区（为什么这么定）

- `AppServer` 只持一个宿主：`this.host = createHost(workspaceRoot, …)`，
  所有 Run、会话、审批都长在这一个宿主上；
- `switchWorkspace` 的语义是"换"：建新宿主 → 换引用 → **旧宿主 `close()`**——
  旧工作区跑着的任务被打断，落一条 cancelled 的 `run_done`；
- 前端 `state.workspace` 是单数，侧栏树只有一个根；工作区记忆
  （`~/.mini-pi/client-workspace.json`）只存最后一个目录。

这么定是因为内核口径就是一个根：工具的 `workspaceRoot`、检索守卫
（`resolveInsideWorkspace` / `isRealPathInside`）、会话落盘、M3 隔离
worktree 全以"一个工作区"为前提。宿主是**天然的作用域单位**——
多工作区不去动这些守卫，只是让宿主可以有几个。

## 2. 什么时候单根不够用

- **来回切会打断**：A 项目任务跑着，切去 B 项目看一眼，A 的任务没了；
- **并行改两个仓库做不到**：除非自己起两个 `serve` 端口、开两个浏览器标签——
  那审批计数、通知、全局并发上限就全散了。

## 3. 目标与非目标

**目标**

- 同时打开多个工作区，各自的会话与任务并存，互不打断；
- **活动工作区**（active root）决定"新任务去哪"、输入区与状态行绑定谁；
  切换活动根**不销毁**其他根的宿主；
- 审批徽标与通知跨工作区聚合；跳转先切活动根，再滚到具体那张审批卡；
- **用户添加的工作区要记住了**：重启客户端后列表原样恢复（活动根也是），
  不用每次重新添加；
- 单工作区用法完全不变（池里只有一个条目时，行为与现在逐字节一致）。

**非目标**

- 不做跨工作区的全局检索，也不做跨会话上下文共享——那是另一个量级；
- 不做多用户 / 远程访问（安全模型仍是只听 `127.0.0.1`）；
- **内核一行不改**：`WorkspaceHost` 仍是"一个根一个实例"，
  Run / RunManager / 审批策略 / worktree 的语义原样保留。

## 4. 服务端：宿主池

| 改动点 | 做法 |
| --- | --- |
| 宿主池 | `hosts: Map<absRoot, WorkspaceHost>`，惰性创建；上限默认 4（可配），超限 409 让用户先关一个 |
| 活动根 | 单独记 `activeRoot`；`POST /api/workspace` 语义从"切换（销毁旧）"改为"打开 / 聚焦（不销毁）" |
| 显式关闭 | 新增 `DELETE /api/workspace?root=…`；跑着 / 排队时回 409（仿照 worktree 丢弃的口径——销毁必须显式，且不被"顺手"触发） |
| 全局并发 | `RunManager` 是 per-host 的（默认 1），多宿主后要加 **AppServer 级总信号量**（默认 2，可配），否则 4 个工作区各跑一个把机器打满；per-host 上限语义保留 |
| 事件载荷 | per-run 流不动；全局流的 `run_state` / `approval_request` / `run_done` 载荷补 `root` 字段（shared/types 加字段，旧前端忽略即可，向后兼容） |
| `/api/state` | 返回所有打开工作区的摘要 + `activeRoot` |

**寻址是关键决策**：`runId`（`run_<时间戳>_<序号>`）进程内唯一，按 id 寻址
即可；但 **sessionId 取自会话文件名**，两个工作区各有一份 `mini-pi-session`
就会撞——所以**所有会话类端点（列表 / 读 / 删 / 续聊）必须先过 root 再查文件**。
落点：query 带 `?root=`（少动路由表），创建类（`POST /api/runs`）带 root 字段。

隔离 worktree 每 Run 挂各自宿主的根，**不受影响**。

### 4.1 工作区记忆：从"记一个"到"记一组"，启动时恢复

需求：用户添加过的工作区**保存下来，下次打开客户端原样加载**。落点是
现成的记忆文件 `~/.mini-pi/client-workspace.json`（`workspaceMemory`
可注入的约定不变，单测仍然不写家目录）：

- **格式**：`{ root }` → `{ roots: [absRoot, ...], active: absRoot }`；
  读到旧格式迁移成单元素列表（active = 那个唯一的 root）。
- **写入时机**：三处——`POST /api/workspace` 打开成功（追加 + 置 active）、
  `DELETE /api/workspace` 关闭成功（摘除）、切换活动根（只改 `active`）。
  与现状一样**先落盘再改内存**（at-least-once 口径），崩溃最多丢一次切换；
  关闭动作里摘记忆也放在收宿主之前——中间崩掉最多是"没关成"，
  不会是"关了又复活"。
- **启动恢复**：`bootAppServer` 在入口接了记忆时调用
  `AppServer.restoreWorkspaces`，把 `roots` 里的条目逐一开进宿主池
  （与打开工作区同一套继承：档位与隔离开关跟人走）。
  **活动根不归恢复挪**：桌面壳的初始根本来就取自记忆的 `active`
  （`resolveDesktopWorkspace` → `readRememberedWorkspace`），显式
  `--cwd` 指定的更不能被记忆压过去——"新任务去哪"以启动时定下的为准。
  记忆为空时维持现状（桌面壳弹目录框问一次）。
- **失效条目**：目录不存在 / 不可读的，启动时跳过建宿主，条目**当场摘除**
  （与方案初稿"保留并标记"不同——侧栏只显示打开的宿主，一条永远开不
  出来的隐形记忆只会让人困惑，也没有落脚点去"手动移除"它）。摘除前写
  日志，不是静默清除。目录有效但起宿主失败的（比如会话目录暂时不可写）
  只跳过、**保留**记忆：路径还在，下次启动再试；超出同时打开上限的同样
  保留——那是"这次没开"，不是"不再要了"。

## 5. 前端：侧栏三层树 + activeRoot

- **state**：`workspace` 单数 → `workspaces: WorkspaceView[]` + `activeRoot`；
  runs / sessions 归组时带根；
- **侧栏**：树的根节点**保持「工作区」不变**（现有 `lv-root` 行：折叠箭头、
  会话计数都保留），它下面变成**多个工作区名节点**——每个工作区名独立折叠、
  独立显示会话数，其下就是会话。层级保持三层：**工作区 → 工作区名 → 会话**；
  与现状的差别只是第二层从"隐含的单工作区"变成显式的工作区名节点，
  **Run 不再作为侧栏叶子**（现状树里的 Run 层去掉，Run 的展示仍归会话
  时间线与状态行）。分区标题旁的 `+` 语义从"换目录"变
  "再打开一个"；工作区名节点的行菜单加「关闭工作区」（跑着任务时禁用并说明）。
- **输入区 / 状态行**：绑定活动根——"新任务去哪"由 activeRoot 回答
  （原第 20 条的分工不变，只是"默认值"的载体多了一层根选择）；
  切活动根不重建时间线，只切侧栏聚焦；
- **时间线仍是会话级**：点别的根下的会话就是换 store，与现在切会话同一条路；
- **审批徽标**：跨根聚合计数，仍按"最早挂起"跳（先 `POST /api/workspace`
  切活动根，再打开对应**会话**——侧栏没有 Run 层了，落脚点从 Run 变会话，
  会话时间线里那张审批卡自然可见）；
- **通知**：`run_done` / 挂起提醒的文案带工作区名——两个项目同时在跑时，
  "任务完成"不说清是谁的就等于没说。

## 6. 分期（每步独立过 `pnpm check`）

1. **W1 服务端**（已落地）：宿主池 + 会话端点 root 作用域 + 事件载荷补 root +
   全局并发信号量。单工作区行为不变，用回归测试钉住（"池里一个条目 = 现状"）。
2. **W2 前端**（已落地）：侧栏三层树（工作区 → 工作区名 → 会话）+ activeRoot +
   审批聚合跳转 + 通知文案带根名。
3. **W3 收尾**（已落地）：工作区记忆列表（含**启动恢复**，见 §4.1）+ 显式关闭 +
   文档同步（本篇、`packages/client/README.md`、`technical-solution.md` §7、
   `client-ui-design.md`）。

## 7. 风险与回归

| 风险 | 防线 |
| --- | --- |
| **会话串根**（root 作用域漏了一处，读写到别的项目的会话）——这类 bug 是静默的 | 回归测试用**两个同名 session 文件**钉住：A 根建的会话，B 根读不到 |
| "切走不打断"改变现有预期 | 文档说清：只有「关闭工作区」才结束里面的任务；切换只挪焦点 |
| 资源：N 个宿主 = N 份 RunManager / 技能扫描 / prompt 组装缓存 | 宿主池上限 + 惰性创建；关闭工作区即释放 |
| 冲突面：`app.ts` / `host.ts` 是改动密集区，`feature/client-ui-redesign` 还没合 | W1 分支晚开、小步合，等 UI 重做合入 main 再动工 |
| 事件载荷加字段 | 只加不改：旧前端忽略未知字段，`shared/types.ts` 的类型是超集 |
| 记忆里目录已失效（被移走 / 卸盘） | 启动跳过建宿主、条目摘除（写日志，不静默）；目录有效但起宿主失败的保留记忆下次再试 |
