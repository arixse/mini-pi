# 客户端 UI 设计稿

> **状态**：设计稿。`packages/client` 目前还没有代码，M2（App Server + Web）才落地。
> 配套静态稿：[`packages/client/design/mockup.html`](../packages/client/design/mockup.html)

> 终态的交互细节与接口语义，落地后以 [cli-interaction.md](./cli-interaction.md)（命令行为）、
> [technical-solution.md](./technical-solution.md)（架构）与

## 1. 定位：客户端不是"网页版 CLI"

最容易做错的一步是把终端那套一比一搬进浏览器。两者约束不同，界面就该不同：

| 维度 | CLI（REPL） | 客户端 |
| --- | --- | --- |
| 同时几个任务 | 一个进程一个回合 | 侧栏里多个 Run 并存，可来回切 |
| 历史 | 靠 `/load` 切会话 | 侧栏直接点，且**只读** |
| 审批 | 阻塞在同一个终端，只能回答当前那个 | 挂起成卡片，可先去看别的任务再回来 |
| 输出呈现 | 逐行流式打印，卡片与状态行 | 结构化时间线，可折叠、可复制、可回看 |
| 等待 | 人就在旁边 | 人可能切走了，所以要有通知与"挂起中"的显式提示 |
| 工作区 | `cd` 进去就是 | 常驻显示，切换要重建宿主 |

由此定下三条原则：

1. **状态永远可见。** 顶栏三枚芯片（工作区 / 默认模型 / 默认档位）+ 待审批计数，再加上运行头里那个 Run 自己的模型（第 20 条），任何时候都能回答"我在哪、用谁在跑、敢让它做什么"。
2. **等待必须被说出来。** 一个"什么都不动"的界面，用户分不清是卡住、是断线，还是在等自己裁决。
3. **界面不做能力墙。** 只暴露两个开关（隔离工作区、委派）。其余能力由模型调工具——把工具做成一排按钮，等于把"模型自己判断该用什么"退回成"人替它选"。

## 2. 信息架构：一屏四区 + 两层浮层

```
┌─ 顶栏 ────────────────────────────────────────────────┐
│ logo  工作区芯片  模型芯片  档位芯片  待审批  [通知][设置][侧栏] │
├──────────┬────────────────────────────────────────────┤
│ 侧栏      │ 主区（时间线，sticky 运行头）                │
│ 新任务    │  用户气泡 / 模型气泡 / 工具卡 / 审批卡 / 提示条 │
│ 搜索      │                                            │
│ 进行中 ─  ├────────────────────────────────────────────┤
│ 历史会话 ─│ 输入区：与会话**同宽**，不横跨侧栏              │
└──────────┴────────────────────────────────────────────┘
浮层：设置·模型 / 工作区选择
```

侧栏竖向贯穿到底，主区与输入区共用第 2 列。实现上是
`grid-template-columns: auto minmax(0,1fr)` + 输入区 `grid-column: 2`，
而不是"整行铺一个页脚"——后者在 flex 一行里很自然，但会把输入框推到侧栏宽度之外。

四区的分工是"谁会一直变"：顶栏是常驻上下文，侧栏是导航，主区是被执行的内容，输入区是唯一的入口。
主区之外的三块都不随执行过程重排，否则每次流式输出都会让人找不到刚才在看的东西。

## 3. 组件与状态清单

| 组件 | 必含状态 | 数据从哪来 |
| --- | --- | --- |
| 顶栏 | 有/无模型、有/无待审批、工作区已选/未选 | `/api/state` + `/api/approvals` |
| 侧栏·任务 | running / blocked / done / failed / cancelled | `/api/runs` |
| 侧栏·会话 | 条数、是否已压缩、排序（时间戳 + 同秒序号） | `/api/sessions` |
| 运行头 | 状态、**模型**、耗时、token、是否可取消 | 当前 Run + 事件流 |
| 用户气泡 | 提交中 / 已入队 | 本地 |
| 模型气泡 | 流式（光标）/ 完成（复制按钮 hover 出现） | `message_update` |
| 工具卡片 | blocked / running / done / failed；结果超 6 行或超长才给"展开全部" | `tool_execution_start / end` |
| 审批卡 | 无风险 / 中等 / 高危；等待中 / 已裁决 / 已失效（Run 被取消） | 内核结构化 `ApprovalRequest`（等级 + 原因 + 摘要） |
| 提示条 | warn（挂起、降级）/ error（流断、请求失败）/ ok（完成、隔离提示） | 本地 + 服务端错误 |
| 输入区 | 空闲 / 忙碌（可停，**输入照常排队**）/ 未配模型（禁用并给理由） | `/api/state` |
| 设置面板 | 未保存 / 保存中 / 已保存；密钥"已配置，留空不改" | `/api/providers`、`/api/model` |

## 4. 稿子里七个界面

| 页签 | 要回答的问题 |
| --- | --- |
| ① 执行中 | 正常态长什么样：流式回复、工具卡、待审批同时出现时怎么排 |
| ② 高危审批 | `rm -rf` 这类怎么呈现，为什么高危不叠加降级理由 |
| ③ 空闲 / 空态 | 没工作区、没模型时界面说什么，而不是一片空白 |
| ④ 历史会话 | 只读回看，与"当前任务"是两套东西 |
| ⑤ 变更 diff | 隔离工作区下改了什么，落地前先看 |
| ⑥ 设置 · 模型 | 密钥只写不读、档位三选一 |
| ⑦ 桌面壳 | 同一份 Web 产物装进原生窗口，业务一行不在主进程 |

## 5. 已定决策

编号与静态稿的标注一一对应。

1. **工作区常驻顶栏。** 模型读写的是哪个目录，任何时候都不能靠猜。
2. **模型与审批档位并排。** "用谁在跑"和"敢让它做什么"是同一组信息，拆到两个面板里就会顾此失彼。
3. **待审批常驻计数 + 一键跳转。** 唯一会让人干等的事件，不能只在时间流里冒出来一次。
   多个 Run 同时挂起时，按**最早挂起**的那个跳，并滚到它时间线里的审批卡——计数是聚合的，落脚点必须是具体那一张。
4. **运行头 sticky。** 滚到长输出中间时，状态、耗时、token 与"停止"始终在手边。
5. **用户靠右、模型靠左，气泡最大宽度 85%。** 长行不贴边，窄屏也不至于挤成一列。
6. **工具卡片四态靠"配色 + 文字"双重编码。** 只看颜色的话，色弱用户与截图场景都读不出来。
7. **工具参数必须渲染。** 只写"跑了 grep"等于让用户信任一句没有证据的话。
8. **风险等级与命中原因由内核算好**（`packages/core/src/risk.ts`），前端只负责配色与按钮。否则同一条 `rm -rf` 在终端和 Web 可能给出不同等级——而等级是安全语义，不容许两端各判一次。
   **「总是允许」的范围同样两端同义**：与 CLI 的 `a` 一样是**本会话内**（不是"本轮"、更不是全局），记账在内核，前端只发选项。
9. **挂起要显式说出来。** 顶部提示条 + 卡片"等待确认"，避免把"在等你"误读成"卡住了"。
   等待时长实时显示；**审批不设超时**——与 CLI 一致，人不在场就一直挂着，超时自动放行或自动拒绝都比"等人"更危险。
10. **高危单独成块（rose），不叠加降级理由。** 一次列五条"删除文件/网络请求"会把最致命的那条淹掉。
11. **窄屏侧栏收成抽屉**，不是挤成一条。挤成一条等于同时失去导航和内容。
12. **输入区只放两个开关。** 见第 1 节原则 3。
13. **没配模型也要能开。** 服务照常起，只是发不出任务。
14. **空态即引导。** 说清缺的是哪一样（工作区 / 模型），并给直达按钮。
15. **历史会话只读。** 切过去就换 store；删除当前会话时服务端顺手开一个新的，不留"当前会话不存在"的死角。删除本身要二次确认。
16. **隔离工作区的 diff 在落地前给。** "改完再决定去留"缺了这一步就只是换了个说法的盲改。
17. **密钥只写不读**，前端永不回显明文；档位认不出时报错而不是回落默认值。
18. **输入区与会话同宽**，不横跨侧栏。输入框是"对话的一部分"而不是页脚：
    跨过去之后，视线必须先越过侧栏宽度才能落笔，长会话里尤其别扭。
    侧栏竖向贯穿到底，主区与输入区共用第 2 列。
19. **输入框默认三行高**（≈84px），随内容长到约八行（208px）后内部滚动。
    一行高写长要求时只见得到开头一截，而这类输入恰恰最需要回看；
    给默认高度而不是只靠自动撑开，是为了让用户**一开始就看出这里能写多段**。
20. **顶栏芯片是"默认值"，运行头才回答"用谁在跑"。** 顶栏的模型/档位芯片说的是
    "新任务会用什么"；每个 Run 实际用的模型画在运行头。侧栏允许多个 Run 并存，
    而"切换后新任务立即生效"意味着不同 Run 可以是不同模型——这时候一枚全局芯片
    答不出"用谁在跑"，所以这个答案必须挂在 Run 上（第 1 节原则 1 的同名说法以此为准）。
21. **运行中输入照常排队，发送不禁用。** 与 CLI 同一口径（busy 时排队、回合结束后
    执行）；排队条目在时间线里标"已入队"。挂起（等审批）与运行中一样能输入——
    终端里做不到这件事，正是客户端"不再阻塞"的那一半价值。
22. **Run 完成后可续聊。** 发送即开新任务、沿用同一会话——Run 是一次执行，会话是
    一段对话，两者不是一回事。隔离工作区的 diff 未落地前，提示条保留，别让"改完
    还没落地"这件事在续聊时被忘掉。
23. **档位切换不追溯。** 只影响之后的工具调用；已挂起的审批卡仍等人裁决，
    既不自动放行也不自动作废。审批是真防线，切换档位不该悄悄改写一次已发出的提问。

## 6. 数据边界：前端不做什么

| 事 | 谁做 |
| --- | --- |
| 风险等级、命中原因 | 内核（`packages/core/src/risk.ts`），前端只配色 |
| 工具调用的摘要文案 | 内核 `describeToolCall`，终端与 Web 说同一句话 |
| 执行编排、取消、并发上限 | 内核（`packages/core/src/run.ts`、`runManager.ts`） |
| 事件流 | 服务端 SSE，按游标续传；断流由前端补一次并给出提示条 |
| 前端不做的 | 不评估风险、不压缩会话、不直连模型、不读密钥明文 |

判据是"这条语义两端必须一致"：凡是一致性有代价的，都由内核产出**数据**，前端只做**呈现**。

**没有令牌门禁。** 服务只监听 `127.0.0.1`，本机自用是主要用法；每开一次浏览器都要贴一次令牌，
换来的是一层"防自己人"的摩擦，不值得——所以稿子不做门禁页。**这条是前提，不是结论**：
哪天要支持非本机访问（局域网、远程开发机），访问令牌是第一批要重新摆上桌的东西。

## 7. 响应式与桌面壳

- **1180**：侧栏常驻（稿子默认）。
- **880**：侧栏仍常驻，主区气泡宽度收窄——这是多数笔记本外接显示器的实际宽度。
- **420**：侧栏变抽屉（overlay + 半透明遮罩），顶栏出现汉堡入口。

桌面壳（M5）不引入第二套界面：主进程只做起服务、开窗口 `loadURL`、关窗退出三件事，
窗口内就是同一份 Web 产物。这样桌面端不会长出"只有桌面端才有的 bug"。

## 8. 待定问题

- **多任务并行时，通知怎么去重**：同一次挂起只提醒一次，还是每个 Run 各提醒一次（倾向后者，但要能一键全清）。
- **通知的形态本身未定**：角标 / 浏览器通知 / 通知面板，稿子里只有顶栏一枚铃铛，没有画出任何一种。
  浏览器通知必须由**用户手势**触发（权限申请），所以界面里还得有"开启通知"的入口——M2 落地时会直接撞上。
- **diff 的粒度**：当前设计是"整个 Run 一份 diff"，可能需要按文件逐个确认合并。
- **合并冲突怎么办**（隔离工作区最大的功能风险）：worktree 隔离期间主工作区自己又改了同一个文件，
  "合并回主工作区"会失败。倾向：**报错并保留 worktree，列出冲突文件**，用户自行处理后再试一次——
  不做自动合并策略，也不静默覆盖。
- **委派（子 Agent）的可视化**：现在是工具卡里的一行，是否要展开成嵌套时间线——取决于 M2 落地后真实调用的密度。
- **历史会话的搜索**：服务端目前没有检索接口，稿子里侧栏的搜索框只覆盖任务名。
